02 Qué incluye el recuento de tokens

El {{cache_pct}}% de todos los tokens procesados fue contexto en caché: el agente releyendo conversación que ya había visto. Por sesión osciló entre el {{cache_lo}}% y el {{cache_hi}}%. Cuanto más dura una sesión, más relee, así que los tokens totales reflejan sobre todo cuánto tiempo siguió trabajando el agente. Por eso la clasificación cuenta tokens de salida.

{{composition}}
  • Alrededor del {{reasoning_pct}}% de los tokens de salida fue razonamiento. El resto son llamadas a herramientas, tests, reescrituras y el código final.
  • Los tokens en caché, los de entrada nueva y los de salida tienen precios distintos, así que ordenar por coste puede dar otro resultado. Los costes son los que se pagaron en su momento.
  • Todo esto sale de un único modelo. Otro modelo podría dar un orden distinto.

03 El recorrido

  1. Una especificación. Un programa de línea de comandos totalmente especificado: JSON de entrada, JSON de salida, determinista y con un conjunto cerrado de códigos de error.
  2. Cinco jugadores. Python, JavaScript, Go, Rust y C. Cada uno tiene su propia sesión de agente, con herramientas, una shell y margen para probarse a sí mismo.
  3. Un árbitro. Una batería de conformidad independiente del lenguaje que solo habla con el binario a través de su CLI. Si no la pasas, tu puntuación no cuenta.
  4. La puntuación. Tokens de salida de la sesión: todo lo que escribió el agente, incluidos el razonamiento, las llamadas a herramientas y las reescrituras.

04 La letra pequeña

Pasar ≠ ser correcto

Todas las entregas pasan los tests puntuados, pero una batería finita no demuestra que el programa sea del todo correcto. Una revisión encontró dos errores en el evaluador, que se corrigieron y se volvió a puntuar. Ningún resultado de aprobado o suspenso cambió.

No es una evaluación cerrada

Algunas especificaciones, tests y oráculos se corrigieron después de examinar las entregas. El historial de Git recoge cada cambio, pero no fue una evaluación prerregistrada.

Confianza, verificada en parte

Los registros completos de las sesiones no se publican, así que ni los totales de uso ni el cumplimiento de las reglas de no copiar se pueden auditar desde el repositorio. El lanzador no es un sandbox del sistema operativo.

05 Contribuir

Todas las entregas y la batería completa de tests están en el repositorio, así que puedes comprobar estas cifras sin ejecutar ningún modelo.

Vuelve a puntuar los resultados

Recompila todas las entregas del repositorio y vuelve a pasar los tests. No hace falta clave de API.

git clone {{repo}}
python3 benchmark/rescore.py

Añade un caso de prueba

Un archivo JSON por comportamiento. Tiene que derivarse de la especificación y pasar contra la implementación de referencia.

benchmark/holdout/<category>/your_case.json
python3 benchmark/runner.py --language oracle

Añade un modelo o un lenguaje

Una ronda nueva para otro modelo, o un adaptador para Kotlin, Swift, Zig, etc. Usa un id de ronda nuevo y sube también las ejecuciones fallidas.

benchmark/rounds/<round>/round.json
benchmark/adapters/<lang>.json
